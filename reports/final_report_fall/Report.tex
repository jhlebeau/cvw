\begin{abstract}
Wearable biomedical devices require processors that balance performance with strict energy constraints, as battery life directly impacts usability and reliability in real world health monitoring. Current solutions often rely on proprietary low power processors, which can be expensive and lack flexibility for customization. Our project proposes an open-source alternative: developing and validating a low power RISC-V processor tailored for biomedical applications. We begin by validating an existing RISC-V core on an FPGA platform to demonstrate full functionality and suitability for wearable workloads. Building on this foundation, we target a 30\% reduction in system power through architectural and implementation-level optimizations. Ultimately, this project aims to produce a validated, energy efficient processor ready for tapeout, enabling more accessible and customizable solutions for biomedical wearables.
\end{abstract}

\begin{IEEEkeywords}
RISC-V, Low-Power Design
\end{IEEEkeywords}

\section{Introduction}
The design goal of this project is to create a processor for use in wearable biomedical devices. Since these devices are battery-powered, they require an architecture that is as low-energy as possible to maximize device usability and reliability.

While low-power processors currently exist, many of these are proprietary, which often makes them restrictive, expensive, or challenging to customize. To address this, the SPARK-V project proposes an open-source alternative using the RISC-V instruction set. The project begins by utilizing WALLY, an existing open-source RISC-V core from Harvey Mudd College, as a baseline [1].

The primary goal is to achieve significant power efficiency, specifically targeting a 30\% reduction in system power. This will be accomplished through systematic architectural and implementation-level power optimizations, culminating in a validated, energy-efficient processor.

\subsection{Design Specifications}

Our goal is to create a fully functional RISC-V processor with ultra low-power usage. In order to minimize power usage, we will need to cut down as many extensions as possible while still keeping the core functionality of the chip. The current design plan specifies the following features:


\begin{itemize}
    \item A \textbf{single-core, single-threaded processor}.
    \item An \textbf{integer-only} instruction set.
    \item Inclusion of the \textbf{base instruction set}.
    \item Inclusion of the \textbf{compressed (C)} instruction set to reduce code memory usage.
    \item Inclusion of the \textbf{minimal multiplication (Zmmul)} extension. This implements multiplication but not division, allowing for increased performance while avoiding the full area requirement of division circuitry.
\end{itemize}

The design specification for the SPARK-V core maintains a high degree of flexibility, prioritizing power efficiency while allowing for targeted performance enhancements. Additional components, such as a dedicated division unit or an instruction/data cache, may be incorporated if testing determines their benefits outweigh the marginal power cost. The decision to include a division unit, for instance, will depend on whether its performance gain in critical biomedical signal processing routines justifies the increased complexity and area overhead, especially since multiplication is already included. Similarly, the incorporation of a cache will be evaluated by comparing its power consumption against the energy savings achieved by reducing external memory accesses. This iterative process, which involves comparing the power usage of several different designs, ensures that the final architecture remains energy-conscious. Therefore, the core will only adopt new extensions or subsystems that offer a substantial, application-specific return on investment in terms of power-to-performance ratio. This also means that future testing will require some examples of programs and routines that are common in biomedical sensors, so that functional unit usage can be measured.

\subsection{Benchmarking Using Embench}
As previously mentioned, testing power and performance requires a set of benchmarks that mimic real embedded workloads. For this purpose, I decided to use Embench, a benchmark set that is specifically targeted to embedded devices without an operating system [3]. Embench contains 19 programs, designed to stress the compute, branching, and memory functionality of the processor differently.

Each program is compiled with two different optimizations: one for maximum speed, and one for minimum code size. The programs are then run, and code size and program speed are measured for both variations. These size and speed values are then compared to the performance on the ARMv7-M processor, which is used as the Embench baseline [3]. Values lower than 1.00 indicate smaller code / slower execution, while values greater than 1.00 indicate larger code / faster execution. The overall score is given by the geometric mean of each program score.

In order to simplify my analysis, I decided to only evaluate the size and speed of the size optimized code. I expect the final design to have a minimal memory size, and thus want my testing to focus on smaller program sizes over performace enhancements. Figure 4 shows the results of the size optimized program for four configurations of the processor. Embench uses control and status registers to measure processor cycles and instructions retired, and thus all tests using Embench require the use of the zicsr extension.

\begin{figure}[htbp]
\centerline{\includegraphics[width=0.9\linewidth]{result_table.png}}
\caption{Embench Size-Opt Results for Various Architectures}
\label{fig}
\end{figure}

Looking at the size results, we can see that the biggest variation is between the architectures that use the compressed instruction (C) extension, and the one that does not. Not having compressed instructions increases the code size by almost 50\%, meaning that the majority of instructions used by Embench are able to be compressed. Adding multiplication (Zmmul) does not seem to have a significant impact on code size, but division and multiplication (M) does provide an approximate 10\% reduction in code size over Zmmul and no multiplication.

For the speed results, we can see that the IMC extensions allow for the best speed, which makes sense as several workloads in Embench contain division. In figure 5, we can see the individiual speed results for each program in the RV32IMC\_Zicsr and RV23I\_Zmmul\_C\_Zicsr configurations.

\begin{figure}[htbp]
\centerline{\includegraphics[width=0.9\linewidth]{RV32IMC_speed.png}}
\centerline{\includegraphics[width=0.9\linewidth]{RV32I_Zmmul_C_speed.png}}
\caption{Individual Embench Program Speed Results With Division (top), and without Division (bottom).}
\label{fig}
\end{figure}

Reducing the set from M to Zmmul reduces performance by about 25\%, showing the value of having a divider unit. However, we can also see the standard deviation increases greatly, which makes sense. Only 6 of the 19 embench programs use division if available, meaning that only these programs experience the performance improvement of the divider unit. This causes the resultant performance of the programs to have greater variation.

The 6 programs that use division are cubic, minver, nbody, st, tarfind, and wikisort. Comparing the speed results of these programs with and without the use of a divider unit, we can see execution speed is reduced by a factor of 2.2-3.9, depending on the specific program and how frequently the division instruction is used.

Removing multiplication further reduces performance, dropping from 0.79 to 0.47 (value compared to ARMv7-M processor). The use of compressed instructions does not change the speed of execution, which is expected.

Overall, this shows the importance of at least the inclusion of compressed instructions for code size and multiplication for code speed. While division is useful in further improving performance for some workloads, the inclusion of division will depend on the expected workloads our processor will use, as programs without division obviously do not benefit from it, and multiplication-based workarounds can be implemented in software if division is necessary. Currently, we expect the programs that will run on this processor will avoid division in almost all cases. Assuming this continues to be true, the divider will likely not be included in the final design. However, this may change in the future.

\subsection{Peripherals}
In addition to these decisions that affect the core of WALLY, I also need to decide how to manage the peripheral connections WALLY contains. As per the GitHub project, these components are referred to as the "uncore" module. These include ROM, RAM, timers, GPIO, and communication over UART. While the design of the core has been specified above, additonal work will be needed to decide which uncore components will be used, and what settings will be applied to them.

Currently, it makes sense to include all of these peripherals to some extent. Program ROM and RAM are fundamental for any standalone system, and the inclusion of PLIC and CLINT enables timer-driven and interrupt-driven execution, both of which are standard requirements for embedded workloads. UART, SDC, and GPIO interfaces also provide practical pathways for off-chip communication, data transfer, and basic system control, making them useful for both development and deployment. In practice, the exact set of peripherals will depend on system constraints. For example, GPIO is flexible and broadly applicable, but the number of exposed pins may need to be reduced if the final processor package has limited I/O availability. Careful selection and scaling of these peripherals will help ensure functionality without exceeding physical or architectural constraints.

\section{Discussion}
At this point in the year, I have been able to set up the needed development environment on ORION and validate the base WALLY design by using it to boot Linux on an FPGA. I also defined an initial architectural specification with the goal of maximizing power-efficiency for wearable biomedical applications. This plan focuses on a minimalist design through the reduction of extensions and add-ons. The current specification is a single-core, single-threaded, integer-only processor utilizing the base instruction set, the compressed (C) extension to reduce code size, and the multiplication (Zmmul) extension (excluding division) for performance. The next focus is to test and finalize the best architectural configuration using compiled designs rather than just RTL simulation. This requires the choice of a Standard Cell Library and the use of Design Compiler, and will give me further ability to compare the power usage of key design elements, such as caches and branch prediction.

Looking ahead to next semester, the project will move into the physical design phase. The primary goal is to start from the optimized architectural configuration and apply implementation-level decisions to achieve the overall objective of a 30\% reduction in system power. Ultimately, the aim is to produce a validated, energy-efficient processor ready for tapeout. I am also looking into additional power-reduction possibilities, including a paper that proposes an entirely battery-less RISC-V processor, which would be an extremely interesting implementation if possible with this design [4]. This could allow for a truly mobile processor for medical applications, but may introduce new challenges.
